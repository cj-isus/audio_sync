## 3. Анализ: что именно берём из каждого проекта

### 3.1 Snapcast — бинарный протокол и время

**Берём целиком модель протокола** (не копируя код, а реализуя заново на Kotlin/Native):

```
BaseMessage: type[2] id[2] refersTo[2] sent_sec[4] sent_usec[4] 
             received_sec[4] received_usec[4] size[4] = 26 bytes header

WireChunk (type=2): timestamp_sec[4] timestamp_usec[4] payloadSize[4] payload[]
  — Каждый чанк содержит timestamp в СЕРВЕРНОМ времени
  — Клиент знает свой offset от сервера (через TimeProvider.serverNow())
  — Планирует воспроизведение: serverNow() == chunk.timestamp + bufferMs

Time (type=4): медианный фильтр DoubleBuffer<200> — берём идею
  — Но заменяем Kalman filter как primary (из ESP32), median как fallback
  — Initial sync: 50 rapid-fire на 100мс, затем каждые 1с

Drift correction: берём модель soft+hard sync
  — Soft: ±0.05% rate adjustment (sample skip/duplicate spread evenly)
  — Hard: при >2ms → fast-forward chunks или play silence
  — Borrow idea: framesCorrection spread across buffer (не 1 glitch, а равномерно)
```

### 3.2 Snapdroid — Android lifecycle

**Берём:**
1. **Foreground service dual pattern**: `startForeground()` + `bindService()` — сервис живёт независимо от Activity
2. **Wake locks**: `PARTIAL_WAKE_LOCK` (CPU) + `WIFI_MODE_FULL_HIGH_PERF` (WiFi throughput)
3. **Init-driven restart**: парсинг логов native процесса → 3s restart timer, но для нас это JNI error callback
4. **mDNS + manual**: NSD как primary, stored host/port как fallback
5. **Snackbar undo**: при отключении устройства — Snackbar с отменой

**НЕ берём:**
- Subprocess architecture (Java запускает .so через ProcessBuilder). Вместо этого используем JNI напрямую:
  - Tight integration с Kotlin
  - Нет IPC overhead
  - Нет парсинга stdout
  - Но crash изолируется через try-catch в JNI

### 3.3 Oboe samples — аудио движок

**Берём:**
1. **FifoControllerBase** — lock-free ring buffer, раздельные read/write counters
2. **ErrorCallback + restart**: `onErrorAfterClose` → 3 retries с 20ms sleep
3. **LatencyTuner**: автоматическая оптимизация buffer size под устройство
4. **getTimestamp()+calculateLatencyMillis()** — точное измерение output latency
5. **Thread affinity**: `sched_setaffinity()` в первом callback — предотвращает glitch при миграции ядра
6. **Format conversion**: Float для processing, let Oboe handle conversion

**Конфигурация Oboe (итоговая):**

```cpp
builder.setSharingMode(oboe::SharingMode::Exclusive)   // low latency
       ->setPerformanceMode(oboe::PerformanceMode::LowLatency)
       ->setFormat(oboe::AudioFormat::Float)            // processing in float
       ->setSampleRate(48000)                           // native для API 26+
       ->setChannelCount(2)                             // stereo
       ->setDataCallback(this)
       ->setErrorCallback(this)
       ->setDirection(oboe::Direction::Output)
       ->openStream(mStream)
```

### 3.4 AirPlay 2 — drift correction через interpolation

**Берём модель feedback loop:**
- Follower записывает: "чанк с timestamp T был реально сыгран в момент A"
- Отклонение `playback_time - scheduled_time` отправляется лидеру
- Лидер компенсирует в timeline anchor для каждого устройства

**Берём interpolation вместо sample stuffing:**
- Вместо "пропустить/дублировать 1 сэмпл" (может дать щелчок)
- Используем mild resampling: `rate_adjustment = ±0.01%`
- Через Oboe можно запросить `setRate()` или сделать resampling в софте (soxr из Snapcast)

**Что это даёт:**
- Ноль audible artifacts при коррекции
- Работает даже на Bluetooth (где jitter большой)
- AirPlay использует этот подход с ~0.5s буфером — мы можем уменьшить

### 3.5 RAAT — endpoint-owns-clock

**Концепция:** не лидер диктует скорость, а каждое устройство само решает. Лидер посылает аудио, фолловеры подтверждают: "я сыграл это сейчас". Лидер адаптирует поток.

**Практическая реализация в нашем контексте:**
- При Local Sync (файл общий) — каждый фолловер владеет своим таймингом
- Лидер только говорит: "сейчас играем семпл X" (timeline anchor)
- Фолловеры дрейфуют независимо, коррекция через drift corrector

### 3.6 ESP32 Snapclient — Kalman filter + minimal parser

**Берём:**
1. **Kalman filter** для time sync (2-state: offset + drift rate):
   - `process_std_dev=0.01`, `drift_process_std_dev=0.0`
   - `forget_factor=1.001`, `adaptive_cutoff=0.75`
   - Initial после 2 samples prediction-correction
   - Даёт намного более стабильный offset чем median filter
2. **Byte-at-a-time parser** — простая архитектура для парсинга бинарного протокола
3. **Initial sync**: pre-buffer queue + wait until age == 0

### 3.7 Opus — stream mode

Когда нужен стриминг (не все устройства имеют файл):

| Параметр | Значение | Источник |
|----------|----------|----------|
| Frame size | 5ms | Opus spec |
| Bitrate | 128kbps VBR | Transparent quality |
| Sample rate | 48kHz | Opus native |
| Complexity | 5-8 | Quality/CPU balance |
| PL | PLC + DRED | Opus 1.5+ |
| Encode | libopus NDK | Snapcast codec chain |
| Decode | MediaCodec (API 21+) | Android platform |

**Stream mode latency budget:**
- Encode: 5ms (Opus frame)
- Network: 1-5ms (LAN Wi-Fi)
- Jitter buffer: 3-5 packets = 15-25ms
- Decode: <1ms (MediaCodec hardware)
- **Total: ~25-35ms** | Для сравнения Snapcast: ~500-1000ms

### 3.8 Android API — networking

| API | Использование | API level |
|-----|---------------|-----------|
| NsdManager.registerService() | Leader announces `_audiosync._tcp` | 16+ |
| NsdManager.discoverServices() | Follower finds leader | 16+ |
| LocalOnlyHotspot | Leader mode без роутера | 26+ |
| SoftApConfiguration (API 33+) | SSID+password control | 33+ |
| WifiLock WIFI_MODE_FULL_HIGH_PERF | Low latency streaming | — |
| MulticastLock | For mDNS, framework handles | — |
| foregroundServiceType=connectedDevice | Required Android 14+ | 34+ |

## 5. Пошаговый план реализации

### Фаза 0: Очистка
- `приложение/` → `app/`
- `ru.аудиосинхронизатор` → `ru.audiosynchronizer`
- Удалить buildSrc (конвенции для одного модуля не нужны)
- Удалить detekt.yml, .ktlint с ГОСТ-бредом — заменить на стандартные
- Удалить невозможные permission-ы из манифеста
- Исправить AGP на реальную версию (8.7.x)
- `kapt` → KSP
- Убрать `android.enableJetifier=true`
- Убрать `org.gradle.java.home` hardcode
- Исправить противоречивые `configuration-cache=true/false`

### Фаза 1: Oboe + C++ (Borrow: Oboe samples, Snapdroid OboePlayer)
- CMakeLists.txt + Oboe prefab dependency
- `audio_engine.cpp` — open/start/stop stream
- `ring_buffer.h` — lock-free SPSC ring buffer (FifoControllerBase pattern)
- `jni_bridge.cpp` — minimal JNI: `native_start()`, `native_stop()`, `native_getLatency()`
- `AudioEngine.kt` — Kotlin wrapper с lifecycle-aware
- Error recovery: `onErrorAfterClose` → 3 retries
- **Результат:** устройство воспроизводит синус/тишину через Oboe callback

### Фаза 2: PCM Playback (Borrow: Snapcast codec chain)
- Decode WAV/PCM файла в Kotlin (MediaCodec или прямой read)
- Filler thread: читает PCM → пишет в ring buffer
- Audio callback: читает из ring buffer → Oboe output
- `DriftCorrector.kt` — placeholder, пока просто passthrough
- **Результат:** приложение играет аудиофайл через native Oboe

### Фаза 3: Clock Synchronization (Borrow: Snapcast + ESP32 Kalman)
- `ClockSynchronizer.kt` — UDP сервер (leader) + клиент (follower)
- NTP 4-timestamp exchange: `offset = ((t2-t1) + (t3-t4)) / 2`
- `KalmanFilter.kt` — 2-state (offset + drift rate)
- `MedianFilter.kt` — DoubleBuffer<200> fallback при |prediction error| > threshold
- Initial sync: 50 rapid-fire at 100ms intervals (Snapcast pattern)
- Steady state: каждые 1-2s
- **Результат:** два устройства знают offset друг друга с точностью <0.5ms

### Фаза 4: Timeline Protocol (Borrow: Snapcast WireChunk + RAAT model)
- Leader рассылает `TimelineAnchor`: mediaTimeUs, deviceTimeNs, sampleRate, state
- Follower вычисляет `serverNow = localNow + clockOffset + drift * (now - lastUpdate)`
- Follower: `schedulePlayAt = anchor.mediaTimeUs + (serverNow - anchorTime)`
- Позиционирование в ring buffer по вычисленному времени
- **Результат:** два устройства играют синхронно (gap < 5ms)

### Фаза 5: Drift Correction (Borrow: AirPlay + Snapcast + ESP32 APLL)
- **Soft (primary):** AirPlay interpolation — resample <0.1% через soxr
  - При 48kHz: ±5Hz = один сэмпл каждые ~10000
  - Плавная коррекция без audible artifacts
- **Soft (fallback):** Snapcast sample skip/duplicate spread evenly
- **Hard (emergency):** при |age| > 2ms → Snapcast hard sync (fast-forward / silence)
- Feedback loop (AirPlay): follower reports actual playout time → leader adjusts per-device offset
- **Результат:** стабильная синхронизация >30 минут, drift <1ms RMS

### Фаза 6: Android Service Layer (Borrow: Snapdroid + Android API)
- `SyncService.kt` — foreground service `foregroundServiceType=connectedDevice`
  - Dual pattern: `startForeground()` + `bindService()`
  - `PARTIAL_WAKE_LOCK` + `WIFI_MODE_FULL_HIGH_PERF` во время стриминга
  - Отключает locks при паузе
- `DiscoveryManager.kt`:
  - Leader: `NsdManager.registerService()` + `LocalOnlyHotspot`
  - Follower: `NsdManager.discoverServices()` + manual IP fallback
  - UI показывает найденные устройства (QR как быстрый способ)
- **Результат:** полноценный background playback + discovery

### Фаза 7: File Transfer + Session Management
- Leader → TCP stream of audio file
- SHA-256 hash для верификации
- Progress bar в UI
- Session state machine: DISCONNECTED → SYNCING → READY → PLAYING → PAUSED
- **Результат:** не нужно копировать файл вручную

### Фаза 8: Stream Mode (Borrow: Opus + Snapcast codec chain)
- Opus encode (libopus via NDK): 5ms frames, 128kbps VBR
- Opus decode (MediaCodec API 21+ или libopus): jitter buffer 3-5 frames
- WireChunk с Opus payload вместо PCM (Snapcast binary protocol)
- **Результат:** leader может стримить любой источник (в т.ч. онлайн)

### Фаза 9: Hardware Latency Compensation (Borrow: AirPlay feedback loop)
- Каждое устройство измеряет `OboeStream.getLatency()` при старте
- Рапортует лидеру
- Лидер рассчитывает per-device offset: `compensation = max(latency) - device_latency`
- Включает в timeline anchors индивидуально для каждого фолловера
- **Результат:** Pixel (12ms) и Redmi (38ms) играют синхронно
