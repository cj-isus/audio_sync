  private var fillerJob: Job? = null

  fun playFile(path: String) {
      val reader = PcmFileReader(path)
      fillerJob = fillerScope.launch {
          while (isActive) {
              val chunk = reader.readNextChunk(FRAMES_PER_CHUNK) ?: break

## Этап 3: Синхронизация часов

**Цель:** Два устройства знают offset своих часов с точностью <0.5ms.

### 3.1 KalmanFilter.kt
- [ ] Создать `sync/KalmanFilter.kt`
- [ ] 2-state Kalman filter: state = [offset, drift_rate]
- [ ] Параметры (из ESP32 Snapclient):
  ```kotlin
  private var processStdDev = 0.01
  private var driftProcessStdDev = 0.0
  private var forgetFactor = 1.001
  private var adaptiveCutoff = 0.75
  private var minSamples = 100
  private var driftThreshold = 2.0
  ```
- [ ] Метод `update(measurement: Double, rtt: Double)`:
  1. Prediction step: offset + drift * dt
  2. Correction step: innovation = measurement - predicted_offset
  3. Если |innovation| > adaptiveCutoff * P → apply forget factor
- [ ] Метод `getOffset(): Double` — текущая оценка offset
- [ ] Метод `getDriftRate(): Double` — текущая оценка drift rate (ppm)
- [ ] Метод `reset()` — сброс при потере соединения
- [ ] **Источник:** ESP32 Snapclient TimeFilter.c

### 3.2 MedianFilter.kt
- [ ] Создать `sync/MedianFilter.kt`
- [ ] DoubleBufferFixedSize<N> — ring buffer фиксированного размера
- [ ] `fun add(value: Double)`
- [ ] `fun median(): Double` — сортировка копии, среднее из mid-N значений
- [ ] `fun clear()` — сброс
- [ ] Размер: 200 (как Snapcast)
- [ ] Используется как fallback когда Kalman нестабилен (первые 2 замера)
- [ ] **Источник:** Snapcast DoubleBuffer

### 3.3 ClockSynchronizer.kt — UDP exchange
- [ ] Создать `sync/ClockSynchronizer.kt`
- [ ] NTP-like 4-timestamp протокол:
  ```
  Follower отправляет:  t1 = nanoTime() (отправка)
  Leader получает:      t2 = nanoTime() (приём)
  Leader отправляет:    t3 = nanoTime() (отправка ответа)
  Follower получает:    t4 = nanoTime() (приём ответа)
  
  offset = ((t2 - t1) + (t3 - t4)) / 2
  rtt    = ((t4 - t1) - (t3 - t2))
  ```
- [ ] Leader side: UDP server на порту 1704, получает запрос → отвечает
- [ ] Follower side: UDP client, отправляет запросы, парсит ответы
- [ ] Initial sync: 50 rapid-fire запросов с интервалом 100ms
- [ ] Steady state: запрос каждые 1 секунду
- [ ] Отбрасывать измерения с RTT > 10ms (jitter в Wi-Fi)
- [ ] Результат подаётся в KalmanFilter (primary) + MedianFilter (fallback)
- [ ] Предпочтение Kalman если minSamples достигнут, иначе median

### 3.4 ClockSync UI — debug screen

- [ ] Переключатель Leader/Follower

## Этап 5: Drift Correction — стабильная долгая синхронизация

**Цель:** Синхронизация держится >30 минут с drift <1ms RMS.

### 5.1 Age computation в audio callback
- [ ] В C++ audio_engine.cpp добавить age computation:
  ```cpp
  // Каждый callback:
  int64_t serverNowNs = localNowNs + clockOffsetNs + (int64_t)(driftRatePpm * (localNowNs - lastSyncNs) / 1e6);
  int64_t scheduledTimeNs = anchorMediaTimeUs * 1000 + anchorDeviceTimeNs;
  int64_t ageNs = serverNowNs - scheduledTimeNs;
  // age = 0 → идеально
  // age > 0 → отстаём (играем позже чем надо)
  // age < 0 → обгоняем (играем раньше чем надо)
  ```
- [ ] Передавать age в drift corrector

### 5.2 DriftCorrector — soft correction (AirPlay interpolation)
- [ ] Создать `cpp/drift_corrector.h`
- [ ] Мягкая коррекция через sample rate adjustment:
  - Если age > 50µs стабильно → play чуть быстрее: rate = 1.0001
  - Если age < -50µs стабильно → play чуть медленнее: rate = 0.9999
  - Максимальная коррекция: ±0.05% (как Snapcast)
  - Spread correction: не разовый skip, а равномерно по всему буферу
- [ ] Реализация в callback:
  ```cpp
  // При framesCorrection > 0 (отстаём — пропустить сэмплы):
  // Читаем frames + framesCorrection, распределяем пропуски равномерно
  // При framesCorrection < 0 (обгоняем — дублировать сэмплы):
  // Читаем frames - |framesCorrection|, дублируем равномерно
  ```
- [ ] **Источник:** Snapcast getNextPlayerChunk + AirPlay resample concept

### 5.3 DriftCorrector — hard sync
- [ ] Hard sync при |age| > 2ms (Snapcast pattern):
  - age > 0 (отстаём): fast-forward — skip чанков/seek до актуальной позиции
  - age < 0 (обгоняем): play silence пока не наступит время чанка
  - После hard sync: reset median buffers, возобновить soft correction
- [ ] Hard sync при |age| > 500ms: emergency — seek до текущей позиции лидера

### 5.4 Age monitoring buffers
- [ ] Три уровня буферов (из Snapcast):
  - miniBuffer: 20 samples — быстрое обнаружение
  - shortBuffer: 100 samples — определение направления drift
  - buffer: 500 samples — долгосрочная стабильность
- [ ] Каждый callback пишет age в буферы
- [ ] Decision logic:
  - hard sync: |buffer median| > 2ms AND |age| > 500µs
  - soft correction: |shortBuffer median| > 100µs AND |miniBuffer median| > 50µs

### 5.5 Feedback loop (AirPlay)
- [ ] Follower периодически (каждые 2s) отправляет лидеру:
  - actual_playout_time: nanoTime() когда чанк реально был воспроизведён (с учётом latency)
  - scheduled_playout_time: когда чанк должен был быть воспроизведён
  - deviation = actual - scheduled
- [ ] Leader: если follower систематически опаздывает → отправляет anchor с超前ным (earlier) mediaTime для этого follower
- [ ] Это компенсирует device-specific задержки без знания hardware latency

### 5.6 JNI: обновить bridge
- [ ] Добавить JNI методы:
  - `nativeSetClockOffset(offsetNs: Long)`
  - `nativeSetDriftRate(ppm: Double)`
  - `nativeSetAnchor(mediaTimeUs: Long, deviceTimeNs: Long)`
  - `nativeGetAgeNs(): Long` — текущий age из C++ для feedback loop

### 5.7 Тестирование
- [ ] Два устройства, один файл, Play на 30+ минут
- [ ] Замерить drift: каждые 5 минут записывать offset
- [ ] Target: drift <1ms RMS за 30 минут
- [ ] Тест с паузами: pause 30s → resume → sync восстанавливается <3s

**DoD:** 30 минут непрерывного воспроизведения на двух устройствах. drift <1ms RMS. Hard sync не срабатывает чаще 1 раза за 10 минут. Pause/resume синхронно.

## Этап 8: Hardware Latency Compensation

**Цель:** Pixel (12ms latency) и Redmi (38ms latency) играют идеально синхронно.

### 8.1 Latency measurement при подключении
- [ ] В `HelloMessage` добавить: `outputLatencyMs: Double`
- [ ] При подключении follower:
  1. Oboe stream уже открыт → `calculateLatencyMillis()` или `getTimestamp()`
  2. Fallback: 50ms если getTimestamp не поддерживается
  3. Отправить в HelloMessage лидеру
- [ ] Leader хранит per-follower latency

### 8.2 Per-device TimelineAnchor
- [ ] Leader при отправке anchor каждому follower:
  ```kotlin
  val compensationUs = (maxLatencyMs - followerLatencyMs) * 1000
  val adjustedMediaTimeUs = anchor.mediaTimeUs - compensationUs.toLong()
  // Follower с большей latency начинает играть РАНЬШЕ → звук доходит одновременно
  ```
- [ ] Или альтернативно: в anchor.deviceTimeNs добавить offset

### 8.3 Feedback loop — actual playout time
- [ ] Follower в feedback сообщении отправляет:
  - `actualPlayoutTimeNs`: nanoTime() + measuredLatencyNs (от Oboe)
  - `scheduledPlayoutTimeNs`: когда должен был играть по anchor
  - `deviationNs`: actual - scheduled
- [ ] Leader: если deviation стабильно > 1ms → скорректировать compensation для этого follower
- [ ] Это AirPlay feedback loop — авто-калибровка без ручных настроек

### 8.4 Тестирование

- [ ] Без compensation: слышимая разница
- [ ] С compensation: синхронно на слух
- [ ] Записать оба устройства на один микрофон → проверить фазу в Audacity

**DoD:** Два устройства с разной hardware latency (>15ms разница) играют синхронно. Фазовый сдвиг в записи <5ms.

## Этап 9: Stream Mode (Opus)

**Цель:** Leader стримит аудио в реальном времени, follower-ы слушают без локального файла.

### 9.1 Opus encoder setup (NDK)
- [ ] Добавить libopus в CMakeLists.txt (через prefab или исходники)
- [ ] Создать `cpp/opus_encoder.h`:
  ```cpp
  OpusEncoder* encoder = opus_encoder_create(48000, 2, OPUS_APPLICATION_AUDIO, &error);
  opus_encoder_ctl(encoder, OPUS_SET_BITRATE(128000));  // 128kbps
  opus_encoder_ctl(encoder, OPUS_SET_COMPLEXITY(8));
  opus_encoder_ctl(encoder, OPUS_SET_VBR(1));
  ```
- [ ] Frame size: 240 samples (5ms при 48kHz)
- [ ] JNI: `nativeEncodeOpus(pcmData: FloatArray): ByteArray`

### 9.2 Opus decoder (MediaCodec fallback)
- [ ] Создать `audio/OpusDecoder.kt`
- [ ] Primary: MediaCodec `"audio/opus"` decoder (API 21+, hardware accelerated)
- [ ] Fallback: libopus NDK decoder
- [ ] Jitter buffer: 3-5 frames (15-25ms)
  - Если packet arrives early → buffer
  - Если packet late → PLC (packet loss concealment)
  - Если packet missing → Opus PLC extrapolates

### 9.3 WireChunk с Opus payload
- [ ] В `protocol/WireChunk.kt` добавить codec field:
  ```kotlin
  @Serializable data class WireChunk(
      val timestampUs: Long,       // server time
      val codec: CodecType,        // PCM, OPUS, FLAC
      val payload: ByteArray       // encoded data
  )
  ```
- [ ] PCM mode: payload = raw float samples (как сейчас)
- [ ] Opus mode: payload = encoded frame, каждый чанк = 1 Opus frame (5ms)
- [ ] Codec negotiation в HelloMessage: supportedCodecs list

### 9.4 Stream pipeline (leader)
- [ ] Источник: MediaCodec decoder (для файла) или Oboe recorder (для микрофона)
- [ ] Читать PCM → Opus encode → WireChunk с timestamp → TCP send
- [ ] Параллельно: играть локально через Oboe output (как обычно)
- [ ] Bandwidth при 128kbps: ~16KB/s — легко для Wi-Fi

### 9.5 Stream pipeline (follower)
- [ ] TCP receive → jitter buffer (ordered by timestamp)
- [ ] Opus decode → PCM float → ring buffer → Oboe output
- [ ] Timestamp-based scheduling: как в Local Sync

### 9.6 Тестирование
- [ ] Leader стримит MP3 файл → follower слушает в реальном времени
- [ ] Latency: <50ms end-to-end
- [ ] Quality: transparent на 128kbps
- [ ] Stress: 3 follower-а одновременно

**DoD:** Leader стримит аудио. Follower слушает с задержкой <50ms. Качество неотличимо от оригинала. 3+ одновременных follower-ов работают.
